# Dictionnaire des données et classification des contraintes

## 1. Hypothèses et choix de modélisation

### 1.1 Tables retenues
Le schéma logique retenu comporte les 10 tables suivantes :

1. `ORBITE`
2. `SATELLITE`
3. `INSTRUMENT`
4. `EMBARQUEMENT`
5. `CENTRE_CONTROLE`
6. `STATION_SOL`
7. `AFFECTATION_STATION`
8. `MISSION`
9. `FENETRE_COM`
10. `PARTICIPATION`

### 1.2 Choix particuliers
- `id_orbite` est retenu en `VARCHAR2(20)` car le jeu de données utilise des valeurs de type `ORB-001`.
- `id_centre` est retenu en `VARCHAR2(20)` car le jeu de données utilise des valeurs de type `CTR-001`.
- `resolution` dans `INSTRUMENT` est **nullable**, car un récepteur AIS peut avoir une résolution non applicable.
- `date_fin` dans `MISSION` est **nullable**.
- `volume_donnees` dans `FENETRE_COM` est **nullable**.
- `AFFECTATION_STATION` est conservée comme table d'association entre centre et station. Pour garantir qu'une station n'appartient qu'à un seul centre, on peut recommander une contrainte supplémentaire `UNIQUE(code_station)`.

### 1.3 Étape 2 - Modèle Conceptuel de Données (MCD MERISE)

#### Entités du MCD
- `SATELLITE` (`id_satellite`, `nom_satellite`, `date_lancement`, `masse`, `format_cubesat`, `statut`, `duree_vie_prevue`, `capacite_batterie`)
- `ORBITE` (`id_orbite`, `type_orbite`, `altitude`, `inclinaison`, `periode_orbitale`, `excentricite`, `zone_couverture`)
- `INSTRUMENT` (`ref_instrument`, `type_instrument`, `modele`, `resolution`, `consommation`, `masse`)
- `MISSION` (`id_mission`, `nom_mission`, `objectif`, `zone_geo_cible`, `date_debut`, `date_fin`, `statut_mission`)
- `STATION_SOL` (`code_station`, `nom_station`, `latitude`, `longitude`, `diametre_antenne`, `bande_frequence`, `debit_max`, `statut`)
- `CENTRE_CONTROLE` (`id_centre`, `nom_centre`, `ville`, `region_geo`, `fuseau_horaire`, `statut`)
- `FENETRE_COM` (`id_fenetre`, `datetime_debut`, `duree`, `elevation_max`, `volume_donnees`, `statut`)

#### Associations et cardinalités (MERISE)
- `SATELLITE` — `ORBITE` : un satellite est sur **une et une seule** orbite `(1,1)` ; une orbite peut concerner **0..N** satellites `(0,N)`.
- `EMBARQUEMENT` entre `SATELLITE` et `INSTRUMENT` (RG-S04), avec attributs `date_integration`, `etat_fonctionnement` :
  - côté `SATELLITE` : `(1,N)` (un satellite embarque 1 à N instruments),
  - côté `INSTRUMENT` : `(0,N)` (un instrument peut être monté sur 0 à N satellites au cours du temps).
- `PARTICIPATION` entre `SATELLITE` et `MISSION` (RG-M03), avec attribut `role_satellite` :
  - côté `SATELLITE` : `(1,N)` (au moins une mission),
  - côté `MISSION` : `(1,N)` (au moins un satellite).
- `PLANIFIE` entre `SATELLITE` et `FENETRE_COM` :
  - côté `SATELLITE` : `(0,N)`,
  - côté `FENETRE_COM` : `(1,1)`.
- `UTILISE` entre `STATION_SOL` et `FENETRE_COM` :
  - côté `STATION_SOL` : `(0,N)`,
  - côté `FENETRE_COM` : `(1,1)`.
- `AFFECTATION_STATION` entre `CENTRE_CONTROLE` et `STATION_SOL` :
  - côté `CENTRE_CONTROLE` : `(0,N)`,
  - côté `STATION_SOL` : `(1,1)` (exactement un centre de contrôle).

#### Justification : relation `FENETRE_COM`, binaire ou ternaire ?
Le choix retenu est **binaire via l'entité `FENETRE_COM`** (et non une association ternaire directe).

Justification :
- Une fenêtre de communication est un **événement métier autonome** (identifiant, début, durée, élévation max, statut, volume).
- Les attributs de fenêtre dépendent de l'occurrence de fenêtre elle-même ; ils ne sont pas de simples propriétés d'un lien `SATELLITE`-`STATION_SOL`.
- En MERISE, cela se modélise proprement par une entité `FENETRE_COM` reliée à `SATELLITE` et `STATION_SOL` par deux associations binaires.
- Cette modélisation facilite aussi l'implémentation des règles temporelles (contrôle de chevauchement) en phase SQL/PLSQL.

#### Intégration de `CENTRE_CONTROLE`
`CENTRE_CONTROLE` est une entité métier à part entière, reliée à `STATION_SOL` par l'association `AFFECTATION_STATION`.
Le besoin métier est : **une station est pilotée par un seul centre**, alors qu'un centre peut piloter plusieurs stations.
La cardinalité retenue est donc :
- `CENTRE_CONTROLE` `(0,N)` <-> `(1,1)` `STATION_SOL`.

#### Note de modélisation : contraintes hors expressivité MCD
Les contraintes suivantes ne sont pas totalement exprimables dans un MCD MERISE et devront être implémentées en Phase 2 via triggers / logique procédurale :
- pas de chevauchement temporel des `FENETRE_COM` pour un même `SATELLITE` (RG-F02),
- pas de chevauchement temporel des `FENETRE_COM` pour une même `STATION_SOL` (RG-F03),
- interdiction d'affecter/planifier un `SATELLITE` de statut `Désorbité` (RG-S06),
- gestion des contraintes dynamiques de statut (ex. station en maintenance, mission terminée).

### 1.4 Étape 3 — Modèle Logique de Données (MLD)

**Légende de notation**

- <u>Attribut souligné</u> : clé primaire (simple ou composite).
- **#FK** : attribut clé étrangère ; la cible est indiquée entre parenthèses (`table référencée.clé`).

---

- Contrainte additionnelle : `UNIQUE(altitude, inclinaison)` (RG-O02).

---

#### `SATELLITE`

`SATELLITE` ( <u>id_satellite</u> `VARCHAR2(20)`, nom_satellite `VARCHAR2(100)`, date_lancement `DATE`, masse `NUMBER(5,2)`, format_cubesat `VARCHAR2(5)`, statut `VARCHAR2(30)`, duree_vie_prevue `NUMBER(4)`, capacite_batterie `NUMBER(6,1)`, id_orbite **#FK** `VARCHAR2(20)` → `ORBITE(id_orbite)` )

---

#### `INSTRUMENT`

`INSTRUMENT` ( <u>ref_instrument</u> `VARCHAR2(20)`, type_instrument `VARCHAR2(50)`, modele `VARCHAR2(100)`, resolution `NUMBER(6,1)`, consommation `NUMBER(5,2)`, masse `NUMBER(5,3)` )

---

#### `EMBARQUEMENT`

`EMBARQUEMENT` ( <u>id_satellite</u> **#FK** `VARCHAR2(20)` → `SATELLITE(id_satellite)`, <u>ref_instrument</u> **#FK** `VARCHAR2(20)` → `INSTRUMENT(ref_instrument)`, date_integration `DATE`, etat_fonctionnement `VARCHAR2(20)`, commentaire `VARCHAR2(4000)` )

---

#### `CENTRE_CONTROLE`

`CENTRE_CONTROLE` ( <u>id_centre</u> `VARCHAR2(20)`, nom_centre `VARCHAR2(100)`, ville `VARCHAR2(50)`, region_geo `VARCHAR2(50)`, fuseau_horaire `VARCHAR2(50)`, statut `VARCHAR2(20)` )

---

#### `STATION_SOL`

`STATION_SOL` ( <u>code_station</u> `VARCHAR2(20)`, nom_station `VARCHAR2(100)`, latitude `NUMBER(9,6)`, longitude `NUMBER(9,6)`, diametre_antenne `NUMBER(4,1)`, bande_frequence `VARCHAR2(10)`, debit_max `NUMBER(6,1)`, statut `VARCHAR2(20)` )

---

#### `AFFECTATION_STATION`

`AFFECTATION_STATION` ( <u>id_centre</u> **#FK** `VARCHAR2(20)` → `CENTRE_CONTROLE(id_centre)`, <u>code_station</u> **#FK** `VARCHAR2(20)` → `STATION_SOL(code_station)`, date_affectation `DATE`, commentaire `VARCHAR2(4000)` )

- Contrainte additionnelle : `UNIQUE(code_station)` (une station rattachée à un seul centre — RG-G04).

---

#### `MISSION`

`MISSION` ( <u>id_mission</u> `VARCHAR2(20)`, nom_mission `VARCHAR2(100)`, objectif `VARCHAR2(500)`, zone_geo_cible `VARCHAR2(200)`, date_debut `DATE`, date_fin `DATE`, statut_mission `VARCHAR2(20)` )

---

#### `FENETRE_COM`

`FENETRE_COM` ( <u>id_fenetre</u> `NUMBER`, datetime_debut `TIMESTAMP`, duree `NUMBER(4)`, elevation_max `NUMBER(5,2)`, volume_donnees `NUMBER(8,1)`, statut `VARCHAR2(20)`, id_satellite **#FK** `VARCHAR2(20)` → `SATELLITE(id_satellite)`, code_station **#FK** `VARCHAR2(20)` → `STATION_SOL(code_station)` )

- Contrainte additionnelle : `CHECK(duree BETWEEN 1 AND 900)` (RG-F04).

---

#### `PARTICIPATION`

`PARTICIPATION` ( <u>id_satellite</u> **#FK** `VARCHAR2(20)` → `SATELLITE(id_satellite)`, <u>id_mission</u> **#FK** `VARCHAR2(20)` → `MISSION(id_mission)`, role_satellite `VARCHAR2(100)`, commentaire `VARCHAR2(4000)` )

---

#### Vérification de la troisième forme normale (3NF)

Pour chaque table, la clé primaire est identifiée ; tout attribut non clé dépend **fonctionnellement et entièrement** de cette clé (pas de dépendance partielle sur une clé composite).

- **`ORBITE`, `INSTRUMENT`, `CENTRE_CONTROLE`, `STATION_SOL`, `MISSION`** : clé simple ; pas de groupe d’attributs répétitif ni de dépendance transitive entre non-clés.
- **`SATELLITE`** : les caractéristiques du satellite ne dépendent pas de sous-ensemble de `id_orbite` ; `id_orbite` est une référence, pas une donnée redondante issue d’une autre table (pas de duplication des attributs d’`ORBITE`).
- **`EMBARQUEMENT`, `PARTICIPATION`, `AFFECTATION_STATION`** : tables d’association (ou de liaison avec données propres au lien) ; `date_integration`, `etat_fonctionnement`, `role_satellite`, `date_affectation` dépendent du couple (ou de la ligne) identifié par la clé primaire composite — pas de dépendance d’un non-clé sur une partie seule de la clé.
- **`FENETRE_COM`** : `id_fenetre` identifie une occurrence ; `datetime_debut`, `duree`, etc. dépendent de la fenêtre, pas de `id_satellite` ou `code_station` seuls. Les FK vers `SATELLITE` et `STATION_SOL` évitent une entité ternaire et ne créent pas de redondance dérivable (pas de transitivité problématique au sens 3NF).

Les cardinalités minimales (ex. au moins une mission par satellite) et règles temporelles (chevauchements) ne relèvent pas de la 3NF : elles sont des contraintes d’intégrité supplémentaires (triggers, assertions applicatives).

---

#### Colonnes candidates à l’indexation

| Table | Index candidats (motivation) |
|---|---|
| `SATELLITE` | `id_orbite` **#FK** (jointures et filtrage par orbite). |
| `EMBARQUEMENT` | `ref_instrument` **#FK** (recherches « instruments par satellite » / contrôles côté instrument) ; `id_satellite` est déjà couvert en tête de PK. |
| `AFFECTATION_STATION` | `code_station` (déjà unique — équivalent index pour contrainte et jointures centre ↔ station). |
| `FENETRE_COM` | `id_satellite`, `code_station` **#FK** (jointures) ; index composites **(`id_satellite`, `datetime_debut`)** et **(`code_station`, `datetime_debut`)** pour requêtes et contrôles de non-chevauchement temporel (RG-F02, RG-F03). `statut` si filtres fréquents par état. |
| `PARTICIPATION` | `id_mission` **#FK** (liste des satellites d’une mission) ; `id_satellite` en tête de PK couvre déjà l’accès par satellite. |
| `MISSION` | `statut_mission`, plage `date_debut` / `date_fin` si tableaux de bord ou filtres temporels fréquents. |

Les clés primaires et contraintes `UNIQUE` génèrent déjà des index en Oracle ; les **#FK** non couverts par la PK méritent en pratique un index si les jointures et les contrôles d’intégrité référentielle sont dominants.

### 1.5 Étape 4 — Réflexion sur l'architecture distribuée

Contexte : NanoOrbit opère sur trois sites (`Paris`, `Singapour`, `Houston`) avec un besoin de continuité d'activité locale et de cohérence globale.

#### Q1. Tables strictement locales à un centre de contrôle

Tables locales proposées :
- `AFFECTATION_STATION` (en exploitation) : chaque centre gère opérationnellement ses stations ; les modifications sont principalement locales au centre responsable.
- une **vue locale de travail** des `FENETRE_COM` futures du centre (fragment local, voir Q3), utilisée pour la planification en cas de coupure WAN.

Justification :
- ces données servent d'abord à l'ordonnancement local des antennes et opérateurs ;
- le besoin est très sensible à la latence (décisions en temps quasi-réel) ;
- les autres centres ont surtout besoin d'une copie de consultation, pas d'écriture concurrente sur ces segments locaux.

> Remarque : au sens strict du MLD, `AFFECTATION_STATION` reste une donnée de référence globale (car visible par tous), mais son **ownership** métier est local au centre affectataire.

#### Q2. Tables globales et mécanismes de synchronisation

Tables à rendre globales (consultables depuis tous les centres) :
- `SATELLITE`, `ORBITE`, `INSTRUMENT`, `EMBARQUEMENT`,
- `MISSION`, `PARTICIPATION`,
- `CENTRE_CONTROLE`, `STATION_SOL`,
- `FENETRE_COM` (au moins en lecture globale, pour éviter des conflits de planification inter-sites).

Mécanismes recommandés :
- **Réplication multi-site avec primaire logique** pour les référentiels critiques (`SATELLITE`, `MISSION`, etc.) :
  - un site maître par domaine (ex. flotte satellites, catalogue missions),
  - réplication asynchrone vers les autres sites pour lecture locale rapide.
- **Réplication bidirectionnelle contrôlée** pour `FENETRE_COM` :
  - écriture prioritairement sur le centre propriétaire de la station,
  - propagation near-real-time vers les deux autres centres,
  - résolution de conflit via règle métier (horodatage + priorité centre propriétaire).
- **Copies en lecture seule** (matérialisées) pour reporting et supervision inter-centres.

#### Q3. Continuité de Singapour si serveur central indisponible

Architecture proposée : **fragmentation horizontale de `FENETRE_COM` par centre propriétaire de station**.

Principe :
- on détermine le centre propriétaire via `AFFECTATION_STATION(code_station -> id_centre)`,
- chaque site stocke et accepte en écriture son fragment local :
  - `FENETRE_COM_PARIS`,
  - `FENETRE_COM_SGP`,
  - `FENETRE_COM_HOU`.
- Singapour planifie en autonomie sur `FENETRE_COM_SGP` même en mode dégradé (serveur central KO).
- au rétablissement réseau : synchronisation différée (CDC/journal des transactions) vers la vue globale `FENETRE_COM`.

Complément utile :
- conserver en local à Singapour une copie (lecture seule, rafraîchie) de `SATELLITE`, `MISSION`, `PARTICIPATION`, `STATION_SOL` pour valider les règles de planification hors ligne.

#### Q4. Risques de cohérence dans un système multi-sites

Risque 1 — mise à jour simultanée d'état satellite :
- Paris passe `SATELLITE.statut = 'Défaillant'` pendant que Houston crée une nouvelle ligne `FENETRE_COM` pour ce satellite.
- Effet : planification incohérente avec le statut réel.
- Mitigation : verrou logique par satellite + contrôle transactionnel au commit + réplication prioritaire des changements de statut.

Risque 2 — double réservation de créneau station :
- Singapour et Paris créent quasi simultanément des fenêtres qui se chevauchent sur la même `STATION_SOL` (données répliquées avec retard).
- Effet : violation RG-F03 détectée tardivement.
- Mitigation : ownership d'écriture par centre propriétaire de station + trigger anti-chevauchement local + file d'arbitrage lors de la resynchronisation.

Risque 3 (optionnel) — divergence d'affectation de station :
- `AFFECTATION_STATION` modifiée sur deux sites avant convergence.
- Effet : une station semble rattachée à deux centres temporairement.
- Mitigation : écriture autorisée uniquement au centre administrateur des ressources globales + contrainte `UNIQUE(code_station)` validée au site maître.

### Remarques métier
- `volume_donnees` doit être renseigné seulement si `statut = 'Réalisée'`
- pas de chevauchement possible pour un même satellite
- pas de chevauchement possible pour une même station

Ces trois dernières contraintes nécessitent un mécanisme procédural.

## 2.10 Table `PARTICIPATION`

| Attribut | Type Oracle | Obligatoire | Unique | Contraintes / Remarques |
|---|---|---|---|---|
| id_satellite | VARCHAR2(20) | OUI | NON | PK composite, FK vers `SATELLITE` |
| id_mission | VARCHAR2(20) | OUI | NON | PK composite, FK vers `MISSION` |
| role_satellite | VARCHAR2(100) | OUI | NON | Rôle joué dans la mission |
| commentaire | VARCHAR(MAX) | NON | NON | Commentaire libre sur la participation du satellite |

### Contraintes de table
- PK(`id_satellite`, `id_mission`)
- FK(`id_satellite`) → `SATELLITE(id_satellite)`
- FK(`id_mission`) → `MISSION(id_mission)`
